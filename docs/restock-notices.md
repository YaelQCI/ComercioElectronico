# Avisos de reposición (#20)

Ficha, tarjetas y guardados de variantes agotadas permiten registrar correo, presentación y consentimiento explícito. Se informa finalidad y que el proveedor sigue pendiente por decisión del propietario. La respuesta confirma únicamente escritura en PostgreSQL; no afirma envío de correo. Sin clave configurada se devuelve error recuperable. No se inventaron productos ni contactos.

Las suscripciones activas se deduplican por correo normalizado/SKU, incluyendo concurrencia. El registro es de invitado y no acepta userId del navegador; asociación a una cuenta queda para #23. Cancelación por enlace protegido e idempotente, con confirmación manual: abrir el enlace no cambia estado. El token viaja en fragmento URL, no en la consulta HTTP, y solo se conserva SHA-256 en la tabla. Se deriva mediante HMAC de una clave privada de 32 bytes base64 (`NUXT_RESTOCK_TOKEN_SECRET`); conservar esa clave mientras existan suscripciones y no versionarla.

La migración adicional `20261014010000_restock_availability` crea la observación persistente por variante, sin modificar la migración inicial. Se aplicó únicamente a la base aislada de pruebas. El modelo suma 58 tablas. Disponibilidad significa producto publicado y stock vendible, sin bloqueo/vencimiento y libre de reservas según zona horaria del almacén. Al observar agotado → disponible se encola un aviso único por suscripción; cambios posteriores se vuelven a comprobar antes de enviar. El aviso no reserva ni promete stock permanente.

`npm run restock:observe` es consulta sin mutaciones. `--apply` observa y encola usando `RESTOCK_SITE_URL` configurada, sin enviar correos. Puede programarse tras desplegar/configurar datos. El muestreo puede no observar cambios transitorios entre ejecuciones; no envía por una disponibilidad que ya desapareció. El ejecutor `processRestock` permite integrar el proveedor elegido con un contrato `send({to,subject,text,idempotencyKey}) → {id}`. No se eligió ni instaló proveedor, no hay envío real ni tarea de entrega activada.

Cola con bloqueos, lease, contador de intentos, espera progresiva, errores saneados y recibo del proveedor. Cancelar antes de que empiece el envío impide notificar. Éxito del proveedor marca suscripción NOTIFIED y mensaje PROCESSED; no se repite esa suscripción. NOTIFIED indica aceptación por proveedor, sin afirmar llegada a bandeja. Una nueva suscripción exige que vuelva a agotarse.

Si el adaptador declara `idempotencyWindowMs`, se reintenta con clave y cuerpo estables dentro de esa ventana con margen de seguridad. Fuera de la ventana o sin idempotencia, un resultado incierto queda FAILED para reconciliación manual, sin reenviar automáticamente. Sin proveedor, no se consumen mensajes ni se registran entregas ficticias. La futura integración debe aplicar timeout menor de 20 segundos y una clave de cancelación estable.

Validación: seis pruebas PostgreSQL específicas cubren deduplicación, consentimiento/correo, hash, transición, concurrencia de ejecutores, cancelación previa, fallo y reintento idempotente, bloqueados/vencidos, proveedor ausente y ventana vencida. Pruebas HTTP/SSR y build se verifican antes del commit. Todas las entregas fueron dobles de prueba; no se enviaron correos reales.

Pendiente para cerrar #20: elección/integración y configuración del proveedor, prueba contractual de envío real autorizada, programación del ejecutor, asociación autenticada #23 y validación visual/teclado/tacto. El propietario indicó explícitamente que todavía no se elija proveedor; por ello estas dependencias permanecen deshabilitadas y el issue debe seguir abierto.
